# Release 0.1.4 (pre-release)

## Overview

Targeted follow-up to v0.1.3 for one field bug: after the rapid-click
power-off freeze fix in v0.1.3, the **confirming button release was still
occasionally not recognized** — the device stayed on the POWER OFF screen with
all buttons dead. This release closes the actual root cause in the button
driver, adds a recovery path, and fixes an adjacent threshold-boundary race.

## Changes

### Power-off release occasionally not recognized (root cause)

After the 3 s max-level long press fires, the driver breaks out of its
polling loop and parks its thread on the GPIO-edge semaphore, still holding
`long_press_triggered` until the physical release emits the confirming
`BUTTON_RELEASE`. Any edge that arrived **during the hold** (contact bounce,
the 1 s haptic motor's mechanical/EMI coupling — the same noise still faintly
audible in the mics) leaves a stale semaphore behind: the thread wakes
immediately, re-polls, sees the pin still pressed, and took the "new press"
branch — which clears `long_press_triggered`. The real release was then
classified as an ordinary click, `BUTTON_RELEASE` never fired, and the app's
power-off latch ate all further input: stuck on the power-off screen, dead
buttons, only recoverable by reboot.

v0.1.3's semaphore drain could not close this: the drain runs once at wake-up
entry, so edges arriving during the 3 s hold survive it and become exactly
these stale wakes.

Fix: while `long_press_triggered` is set (the "fired, waiting for the
confirming release" state), the driver no longer registers a new press on a
wake that sees the pin pressed — it just keeps polling. State-machine
invariant: the flag can now only be cleared by emitting `BUTTON_RELEASE`, so
the confirming release cannot be swallowed regardless of glitch source.

### Stuck power-off screen: 3 s hold retries instead of bricking input

Defense in depth in the app's input gate: if the confirming `RELEASE` is ever
lost by some unforeseen path, the power-off latch previously ignored all
button input forever. A fresh max-level long press (LEVEL 1–3) is now allowed
through as a retry — re-arming the power-off confirmation instead of leaving
the device dead. Re-posting POWER_OFF_SHOW is idempotent.

### 3 s threshold-boundary race: hold-for-power-off could start a recording

The driver polls the button every 30 ms. A release landing in the poll gap
right after the 3 s mark (before the auto-fire poll caught it) was handled by
the level-0 deferred path and emitted `BUTTON_RELEASE` with the power-off
never triggered — so a deliberate 3 s power-off hold occasionally **started a
recording** instead. The level-0 release path now fires the max-level
callback first when the held duration already crossed the max threshold, then
emits the release: the app sees the power-off level and the confirm in the
correct order.
